wiki page를 만들거나 고치기 전에 이 파일을 읽는다. `create_wiki_page`와 `update_wiki_page`의
계약이다. 아무도 자동으로 붙여주지 않는다.

## 페이지는 콘텐츠를 이해하려고 여는 것이다

읽는 사람은 주제를 이해하려고 연다. claim이 어떻게 승격됐는지, verified가 왜 없는지는 그 사람이
지금 알아야 할 정보가 아니다. **vault 운영 정보는 전부 맨 아래 `---` 밑으로 내린다.**

2026-08-28에 이 규칙 없이 7장을 썼다가 사용자가 물렸다. 페이지 두 번째 줄이
`## Verified Knowledge`였고 그 밑에 "블로그 하나가 근거라 승격 금지"가 적혀 있었다. 주제를
읽으러 온 사람에게 vault 내부 사정을 먼저 보여준 셈이다.

## 구조

```
(리드 문단: 이게 뭐고 왜 보는가)

## 한눈에        긴 페이지만. 3~5줄, 결론부터
## <내용 제목>    Active Parameter, 두 가지 배치 방식, 무너지는 지점 ...
## 한계          내용을 오해하지 않으려면 알아야 할 것 (측정 조건, 원문이 안 다룬 것)
## 더 볼 것       관련 페이지 (선택)

---

## 근거          절별 claim 표, 출처 링크, 검증 상태
```

제목은 전부 **내용 제목**이다. `Verified Knowledge`, `Claims / Opinions` 같은 vault 용어를
제목으로 쓰지 않는다. `## 한눈에`는 짧은 페이지에는 넣지 않는다. 모든 장이 같은 틀로 시작하면
그것도 템플릿 티가 난다.

설계 문서 §3.5가 권장하는 섹션 목록(`Verified Knowledge` / `Project-Specific Notes` /
`Claims / Opinions` / `Caveats` / `Common Misconceptions` / `Learning Notes` / `Sources`)은
2026-08-28에 버렸다. 그 문서를 읽고 그대로 따라가면 사용자가 이미 물린 형식으로 되돌아간다.
버려도 안전한 것은 확인했다. 코드에 그 제목을 파싱하는 곳이 없고, `answer.md`도 claim의
status를 읽지 페이지 제목을 읽지 않는다.

## 본문에 claim id를 박지 않는다

문장마다 `[claim-20260827-013]`이 붙으면 읽는 흐름이 끊긴다. 맨 아래 `## 근거` 표에 절 단위로
모은다.

```markdown
| 절 | claim |
| --- | --- |
| Active Parameter | claim-20260827-001, claim-20260827-002 |
```

`claim_refs` frontmatter에 든 id 집합과 본문에 나오는 id 집합이 정확히 같아야 한다. 한쪽에만
있으면 근거를 되짚을 수 없거나 없는 근거를 주장하는 것이다.

## 출처는 파일명으로 링크한다

```markdown
출처: [[Expert Parallel Deployment 이해하기]] (Wongi Baek, Medium, 2026-07-25)
```

source 파일명은 원문 제목이다(`prompts/ingest.md` 참조). `[[source-20260827-001]]`은 파일명이
아니라 id라서 링크가 안 걸린다. 링크로 걸어야 Obsidian 그래프에 page -> source 엣지가 생기고,
"이 글 하나에서 주제가 몇 개 갈라졌나"가 보인다.

## 검증 상태는 아래에 한 줄로

```markdown
검증 상태: 근거 claim 8건 모두 `accepted_for_now`. verified는 없다.
```

무엇으로 대조하면 verified로 올릴 수 있는지도 알면 같이 적는다 (공식 문서, 공개 코드 등).
`accepted_for_now`와 `attributed`는 "검증됐다"가 아니라 "지금은 이대로 받아들인다"는 뜻이므로
본문에서 확정처럼 쓰지 않는다.

## 문체: 사람이 쓴 것처럼

- **`**라벨**: 설명` 형태의 불릿을 쓰지 않는다.** AI가 쓴 티가 제일 크게 나는 자리다.
- 대구를 맞추지 않는다. "A는 X하고 B는 Y한다"가 이어지면 문단이 기계처럼 읽힌다.
- "이것이 ~이다", "핵심은 ~이다" 같은 껍데기를 걷어낸다.
- 숫자를 먼저 던진다. "GLM-5.2는 744B짜리인데 한 번 계산에 쓰는 건 40B, 약 5.4%다."
- 짧게 끊는다. "all-to-all이 두 번이다. EP가 치르는 값이 여기 있다."
- 독자에게 말을 건다. "여기서 헷갈리기 쉽다", "숫자를 넣어보자."
- 괄호로 풀어 쓴다. "DP(Data Parallel, 그냥 replica라고 봐도 된다)."
- 놀란 지점은 놀란 것처럼 적는다. "속도는 마케팅과 반대로 갔다."
- `—`(em dash)와 `·`(가운뎃점)를 쓰지 않는다.

## `## 한계`에는 새 주장을 넣지 않는다

한계는 출처가 무엇을 다루지 않았는지, 어떤 조건에서 잰 값인지를 적는 자리다. 내 기술적 추측을
근거 없이 적으면 그것도 claim인데 ledger를 안 거친 claim이 된다. "원문은 이 조건을 다루지
않는다"는 되고, "이 경우엔 손해일 것이다"는 안 된다.

## 본문을 다시 타이핑하지 않는다

한 줄 고치겠다고 4KB짜리 본문을 도구 인자로 다시 적으면 거기서 문장이 조용히 바뀐다.
`update_wiki_page`의 **`body_path`**에 파일 경로를 넘긴다. 고칠 내용을 스크립트로 만들어
파일에 쓰고 그 경로를 주면 옮겨 적는 단계가 없어진다.
